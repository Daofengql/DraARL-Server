# 幽灵多收与消息查询性能验证

本文记录 2026-08-06 在 Hyper-V Ubuntu VM 中对幽灵多收路由和频道消息查询执行的可复现性能验证。数据用于比较实现方案和发现数量级问题，不是生产 SLA；真实网卡、生产数据分布和在线 DDL 仍需在目标环境复测。

## 测试环境

| 项目 | 配置 |
|------|------|
| 操作系统 | Ubuntu 22.04 VM |
| CPU | AMD Ryzen 9 7940HX，VM 分配 8 vCPU；Go 基准固定 `GOMAXPROCS=4` |
| 内存 | 7.8 GiB |
| Go | 1.25.5 linux/amd64 |
| MySQL | 8.4.10，Docker，同一 VM |
| 消息数据 | 1,000,000 行，4 个群组，语音/文本各 50% |

## 多收 fan-out

以下数据取 5 次 `300ms` Go benchmark 的中位数。`locked_scan` 模拟每帧遍历全部 Session 并复制目标的旧式热路径；`cached_plan` 是当前按通信域缓存不可变接收计划的热路径。

| Session 数 | 方案 | 延迟 | 内存/操作 | 分配/操作 |
|-----------:|------|-----:|----------:|----------:|
| 10,000 | 全表锁扫描 | 429.10 us | 989 KiB | 3,999 |
| 10,000 | 缓存命中 | 27.02 ns | 0 B | 0 |
| 20,000 | 全表锁扫描 | 840.05 us | 1.92 MiB | 7,999 |
| 20,000 | 缓存命中 | 27.57 ns | 0 B | 0 |

10,000 和 20,000 Session 下缓存命中分别约快 15,900 倍和 30,500 倍。20,000 Session 的完整缓存重建中位数为 11.25 ms、16.95 MiB 和 40,499 次分配；该成本只在路由或会话发生变化后支付，不进入每个媒体帧的稳定热路径。

现代幽灵专项基准使用 1,000 个 Session、32 个通信域、每 Session 订阅 4 个域。每个域恰有 125 个接收 Session：

| 操作 | 中位延迟 | 内存/操作 | 分配/操作 | 结果 |
|------|---------:|----------:|----------:|------|
| 全域缓存构建 | 1.91 ms | 2.66 MiB | 11,024 | 1,000 Session / 4 接收域 |
| 缓存命中 | 28.24 ns | 0 B | 0 | 125 目标 |
| 完整 UDP fan-out | 978.49 us | 632 B | 5 | 排除来源后 124 次发送，错误为 0 |

该专项基准逐帧等待完成，没有出现队列拒绝或发送错误。持续过载时的完整帧淘汰率沿用同一 UDP writer 后端，其稳态与过载数据见[UDP 转发压力测试](UDP单机转发压力测试.md)；本次微基准不能替代真实网络 soak。

复现命令：

```bash
GOMAXPROCS=4 go test ./internal/interconnect -run '^$' \
  -bench '^(BenchmarkEdgeReceiverCollection|BenchmarkModernGhostMultiReceiveFanout)$' \
  -benchmem -benchtime=300ms -count=5
```

## 接收放大模型

默认限制为每账号最多 8 个幽灵 Session、每 Session 最多 16 个接收频道。路由索引最多保存 `8 x 16 = 128` 个“账号-Session-频道”成员关系，但单条频道消息会按 Session 去重，因此不会再乘一次订阅数：

- 单账号在同一热门频道上的单消息最多产生 8 份下行。
- `H` 个账号都达到 8 Session 时，单频道 fan-out 上界约为 `8H`，再排除精确来源 Session。
- 16 个频道同时各产生一条消息时，单账号最坏接收 128 份；这是并发频道数造成的总量，不是单消息重复投递。
- 缓存构建和内存规模与 Session 接收成员关系总数相关；单帧发送成本与该来源频道的去重 Session 数相关。

因此容量规划应分别使用“总成员关系”评估缓存重建和内存，用“最热门频道的去重 Session 数 x 实际包速”评估稳定 fan-out，不能直接把 Session、订阅数和频道人数无条件相乘。

## 百万行频道消息

测试游标位于数据尾部附近，用来验证深分页不会随页码线性退化。无类型过滤始终使用 `idx_comm_records_group_status_start_id(group_id,status,start_time,id)`；带 `message_type` 过滤使用新增的 `idx_comm_records_group_status_type_start_id(group_id,status,message_type,start_time,id)`。

增加类型索引前，某个频道没有目标类型消息时需要扫描 225,000 个索引项，单频道空结果约 2.19 s，四群组合并 50 条约 4.08 s。增加类型索引后的结果如下：

| 查询 | 类型索引前 | 类型索引后 |
|------|-----------:|-----------:|
| 无类型过滤，四群组取 50 条 | 25.78 ms | 22.53 ms |
| 文本过滤，单频道空结果 | 2.19 s / 扫描 225,000 行 | 0.011 ms / 覆盖索引空范围 |
| 文本过滤，四群组取 50 条 | 4.08 s | 10.16 ms |

类型过滤的四群组查询提高约 400 倍，并消除了稀疏类型分布下的大范围回表，因此保留新增索引。百万行造数时间由一次运行的 17.33 s 增至 21.50 s，约增加 24%；该数字同时受缓存状态影响，只能说明额外索引存在写放大，不能代替生产数据副本上的 DDL 持锁、磁盘增量和持续写入验证。

复现命令要求独立且可删除的 `draarl_test_` 前缀数据库：

```bash
DRAARL_MESSAGE_PERFORMANCE_E2E=true \
DRAARL_TEST_MYSQL_DSN='<test-dsn>' \
go test ./internal/gormdb -run '^TestMillionRowMessageCursorPlanMySQL$' -v -count=1
```

## 结论

- 多收路由应继续使用按通信域缓存、按 Session 去重的接收计划；每帧重新扫描 Session 不具备扩展性。
- `message_type` 必须使用独立复合索引，否则稀疏类型频道会出现秒级深游标查询。
- 新增索引会增加写入和迁移成本，发布前仍需在生产数据副本记录在线 DDL 时间、额外磁盘和回滚窗口。
- 本轮只改变 fan-out 路由和数据库索引，不改变 DraARLv1 的 90 字节包结构或标准 UDP 实体设备行为。
