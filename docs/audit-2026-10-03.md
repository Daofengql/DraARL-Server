# DraARL Server 全面审计报告（2026-10-03）

## 结论

本次审计基于本地 `dev` 分支 HEAD `7d62762`（`v2.0.0-alpha14`），在 Ubuntu Hyper-V 虚拟机中启动实际服务，并使用浏览器、HTTP API、WebSocket、MySQL/Redis/MinIO 和 UDP 模拟器验证。审计没有修改业务源代码；只创建了临时测试库、测试用户、临时配置和截图。

当前最需要处理的项目：

1. **高：禁用后重新启用不会吊销旧 refresh token。** 已通过正式“管理员切换登录”接口取得 refresh token，禁用用户、重新启用后，旧 refresh token 仍可刷新出新 access token。
2. **高：JWT 仅绑定用户名，没有绑定用户 ID/会话版本。** 用户改名后将旧用户名分配给新用户，旧用户的 access token 会被中间件按用户名加载成新用户。本次实测旧 token 返回了新用户 ID 18。
3. **高：Gin 默认信任任意 `X-Forwarded-For`。** 验证码限流以 `c.ClientIP()` 为键；同一来源前 5 次返回 200、第 6 次起 429，但改写 XFF 为不同地址后连续请求均返回 200。
4. **中：通联日志编辑不能清空可选字段。** `UpdateLogbook` 仅在字段非空时更新；备注清空保存后重新打开仍有旧值。
5. **中：初始化公共频道的数据库契约不一致。** 内存默认频道是 ID 999，但新库只做迁移而没有公共频道记录时，WebSocket 首次连接尝试写入偏好会触发外键错误并显示“初始化失败”。补齐 999 后连接恢复。
6. **中：当前 Go/Node 依赖存在待升级项。** `govulncheck` 在 Go 1.25.5 上报告 31 个标准库/模块漏洞条目，其中部分为导入模块但不可达；可达路径需按发布构建重新跑。生产依赖 `npm audit --omit=dev` 报 1 个 high：`axios 1.13.6`，修复版本范围为 >=1.19.1（需确认浏览器端实际受影响面）。

## 已确认的问题

### A1 — refresh token 在禁用再启用后仍然有效（高）

代码位置：[auth_user_admin.go](../internal/handler/auth_user_admin.go:288) 的 `UpdateUserStatus`。禁用分支只执行 Ghost session/路由吊销与用户缓存失效，没有调用已有的 `revokeUserRefreshSessions` / `RevokeAllByUser`。刷新接口本身只会在刷新时检查用户状态，所以“禁用期间未刷新，随后重新启用”的旧 token 会继续有效。

复现结果：

- 管理员切换到测试用户 2，保存旧 access/refresh token。
- `PUT /api/admin/users/2/status {status:0}`：200。
- 旧 access：403（这是正确的即时状态检查）。
- `PUT .../status {status:1}`：200。
- 旧 access：200。
- 旧 refresh `POST /api/auth/refresh`：200（问题）。

建议：禁用、删除、拒绝审批、角色/用户名等身份变化都调用统一的 `revokeUserRefreshSessions(user.ID, reason)`；增加“禁用→启用旧 refresh 必须 401”的回归测试。

### A2 — JWT 用户名复用导致旧 token 身份漂移（高）

代码位置：[jwt.go](../pkg/jwt/jwt.go:49)、[middleware/auth.go](../internal/middleware/auth.go:47)。JWT claims 只有 `Username` 与角色；中间件验证后调用 `loadUserByName(claims.Username)`。用户改名/删除后如果旧用户名再次被注册，旧 token 会取得新用户对象。

实测：

- 测试用户 2 的 access token 中用户名为 `audit20261003_01`。
- 将用户 2 改名并创建新用户 18，复用 `audit20261003_01`。
- 原 token 请求 `GET /api/me` 返回 200，返回 `id=18`。

建议：access/refresh 会话绑定不可变 user ID；JWT 增加 `sub=user.ID`，中间件按 ID 查询；同时增加用户会话版本/凭据版本，在删除、改名、角色、状态和密码变化时递增并校验。旧 token 不能因用户名复用而切换身份。

### A3 — 任意 XFF 可绕过 IP 限流（高）

代码位置：[server.go](../internal/server/server.go:29) 使用 `gin.New()`，没有配置 `SetTrustedProxies`；多个限流器使用 `c.ClientIP()`。

实测同一来源调用 `GET /api/captcha`：

- 不带 XFF：前 5 次 200，之后 7 次 429。
- 分别带 `X-Forwarded-For: 198.51.100.N`：6 次均 200。

建议：直连部署显式 `SetTrustedProxies(nil)`；反代部署只信任明确的代理网段，并要求代理清理/重写 XFF。增加回归测试，确认伪造 XFF 不会改变限流键。该问题还会影响访问日志中的客户端 IP。

### A4 — 通联日志可选字段无法清空（中）

代码位置：[logbook.go](../internal/handler/logbook.go:282-392)。更新处理对 `Notes`、QTH、设备、天馈、RST 等字段统一使用 `if req.Field != ""`，无法表达“清空字段”。

实测：新增日志备注“用于验证编辑后能否清空”，编辑将备注置空并保存，再次打开仍返回原备注。

建议：更新请求使用指针字段（`*string`、`*int`）区分“未提供”和“显式空值”，或使用字段掩码；补充 API/UI 回归测试。

### A5 — 默认频道 999 依赖隐含数据库状态（中）

代码位置：[protocol.go](../internal/models/protocol.go:67)、[udphub/group.go](../internal/udphub/group.go:27)、[ghost_client_preference.go](../internal/gormdb/ghost_client_preference.go:75)。

内存层硬编码公共频道 999；偏好表对 `tx_group_id` 有外键。但迁移没有保证 `public_groups(id=999)` 存在。全新测试库首次打开 /radio 时，日志出现：

`Cannot add or update a child row ... ghost_client_preferences ... tx_group_id=999`

浏览器显示“初始化失败”、WebSocket 401。手动创建 999 后同一流程变为“已连接”。

建议：把公共频道作为显式幂等种子数据/迁移步骤，并验证外键与缓存数据一致；启动健康检查应在缺少必要系统数据时明确失败原因，而不是在首次用户连接时失败。

### A6 — 前端在 HTTP 下无法使用浏览器音频/麦克风（部署风险，中）

实测 `http://172.30.50.2:29001/radio`：`isSecureContext=false`、`navigator.mediaDevices=false`。页面只能显示“点击激活”，音频/麦克风能力不可用。生产若经 HTTPS 则属于正常浏览器安全策略；开发部署文档应明确要求 HTTPS 或 localhost，并在 UI 中显示“当前连接不是安全上下文”的可操作提示。

### A7 — 依赖安全基线需要更新（中）

- `npm audit --omit=dev`：1 个 high，`axios 1.13.6`，修复版本范围 >=1.19.1。需要升级并重新构建，确认是否为 Node adapter 专属问题。
- `govulncheck` 使用 VM Go 1.25.5：报告 31 个漏洞条目，涉及 Go 标准库（例如 net/http、crypto/tls、net/url、mime、encoding/xml）以及 `golang.org/x/image`、`golang.org/x/net`、`github.com/redis/go-redis/v9@v9.7.0`。其中工具输出明确的代码可达路径包含 go-redis 的 `CLIENT SETINFO` 连接建立路径；其余条目需用发布构建、升级后的 Go 工具链重新核验。
- 当前依赖 `go-redis/v9 v9.7.0`，工具报告修复版本 v9.7.3。

优先先升级 Go toolchain 到包含修复的版本，再升级 go.mod 依赖；将 `govulncheck`、`npm audit --omit=dev` 纳入 CI。

## UI/可用性问题

### U1 — 平板宽度仍使用完整桌面导航（中）

[home-768x1024.png](../output/playwright/home-768x1024.png) 中顶部 6 个导航项在 768px 宽度全部展开，中文出现“首/页”“中继查/询”“技/术交流”等竖向折行；控制台按钮也被挤窄。代码在 [PublicHeader.tsx](../www/src/components/layout/PublicHeader.tsx:130) 以 `sm`（600px）作为桌面断点，实际应把完整导航推迟到 md 或设置平板紧凑菜单。

### U2 — 设备页手机操作区拥挤并出现横向滚动（中）

[devices-390x844.png](../output/playwright/devices-390x844.png) 显示标题、自动刷新、动态码绑定、设备密码、预配置工具在同一顶部区域；设备表格只能横向滚动，用户必须拖动到底部查看列。建议手机端将操作按钮折叠为菜单/分行，把表格改为卡片或固定关键列。

### U3 — 用户管理手机表格的列内容叠在一起（中）

[edit-user-mobile-open.png](../output/playwright/edit-user-mobile-open.png) 及 [edit-user-mobile-settled.png](../output/playwright/edit-user-mobile-settled.png) 显示 390/320 宽度时表格通过溢出裁剪，部分用户名、角色列在状态列下方透出/重叠，横向滚动条不能让用户直观看到完整行。建议移动端使用卡片列表；弹窗本身可用，但应增加 `max-height`/滚动焦点管理。

### U4 — 注册步骤条在手机上逐字竖排（中）

[register-390x844.png](../output/playwright/register-390x844.png) 显示 4 个中文步骤标签挤成窄列。移动端使用 `alternativeLabel`、紧凑进度指示（如“第 1/4 步”）或隐藏文字标签。

### U5 — 图标按钮缺少可访问名称（低）

普通布局和后台布局中多个 `IconButton` 只有图标，没有 `aria-label`。Playwright snapshot 对顶部菜单、刷新、操作按钮均显示为无名称 button；代码位置 [PublicHeader.tsx](../www/src/components/layout/PublicHeader.tsx:97-263)。键盘/读屏用户无法知道这些按钮用途。补充 aria-label、tooltip 与焦点样式。

### U6 — 文档版本滞后（低/产品一致性）

浏览器 [docs-1440x900.png](../output/playwright/docs-1440x900.png) 实际显示公开文档为 alpha4；源码 [device-protocol.md](../www/public/docs/device-protocol.md:3) 仍为 `v2.0.0-alpha4)，而仓库 [README.md](../README.md:21) 为 `v2.0.0-alpha14`、[docs/Protocol.md](../docs/Protocol.md:3) 为 alpha5。应统一文档来源或在构建阶段自动生成/校验版本。

### U7 — 移动端注册/登录卡片垂直空间偏紧（低）

320×568 登录页中验证码登录 tab 折成两行，登录按钮需要滚动后才能看到；注册页也需要较多纵向滚动。不是功能阻断，但可通过减小 `PublicPageLayout` 的双层 padding、简化 tab 文案和移动端表单间距改善。

### U8 — 通联日志弹窗在 768×1024 仍是长滚动表单（低）

[logbook-dialog-768x1024.png](../output/playwright/logbook-dialog-768x1024.png) 中底部固定按钮可用，但大量字段需要在弹窗内部滚动；可将“对方信息/我方信息”拆成步骤或使用抽屉，移动端尤其明显。

## 性能结果

- HTTP（测试服务、MySQL/Redis 本地容器，20 并发 × 400 请求）：`/healthz` 约 1735 req/s，p95 16.4ms；`/api/me` 约 1743 req/s，p95 17.3ms；`/api/users` 约 1901 req/s，p95 16.3ms；通信趋势约 1930 req/s，p95 15.0ms。结果仅反映 VM 本地环境。
- UDP fan-out：100/500/1000 客户端，120ms 语音包间隔，0% 丢包；1000 客户端时服务进程约 0.13 CPU core、RSS 55MB，延迟平均 1.25ms、P95 <=2ms。未代表跨主机、跨边缘、音频转码或真实公网。
- 120,000 条通信记录全局分页性能测试约 13.2ms。
- 1,000,000 条消息游标查询：单组/四组 typed query 约 246–458ms；已有覆盖索引有效，但四组未带类型的查询明显较慢，建议保持 message_type 条件。
- 服务启动时 UDP socket buffer 实际受宿主机 sysctl 限制为约 425,984 bytes（请求 4MiB），部署容量需按系统内核参数核对。
- `replayWindow.accept` 在 [replay_window.go](../internal/interconnect/replay_window.go:36) 对最大 16,383 的消息 ID 跳跃逐条清理位，认证互联节点触发时会持锁循环；建议按字批量移动/清零。

## 其它审计结果

- API 未登录访问均正确返回 401；普通用户访问管理员资源返回 403；跨用户读取通联日志返回 404。
- CORS 对不允许的 Origin 返回 403，允许来源返回 204 且带 credentials。
- 上传存储已拒绝 HTML/SVG/脚本类型，并做路径穿越与对象权限校验；未发现直接存储型 XSS。
- refresh token 轮换与重放检测在正常路径有效；密码修改后旧 refresh 正确 401。
- 发现的集成测试失败：
  - `TestBroadcastManagementHTTPE2E`：手动播报被判定 `skipped_no_receiver`，测试没有建立真实接收者会话。
  - `TestBroadcastSchemaMigrationMySQL`：测试在重复/迁移状态下预期的 policy 回填未满足。需单独修测试夹具或迁移逻辑，不能忽略。
- 当前未运行 release 生产配置下的公网/跨边缘压测；未验证真实 SMTP、Keycloak、MinIO 外网 TLS、APRS 与 FFmpeg 长时负载。

## 建议修复顺序

1. A1–A3：统一会话吊销、JWT 改用不可变 user ID/版本、配置可信代理；补回归测试。
2. A5：把 ID 999 公共频道变成正式幂等迁移/种子并加启动自检。
3. A4：修复可选字段显式清空语义。
4. A7：升级 Go/toolchain、go-redis、axios，并固定 CI 漏洞扫描。
5. U1–U4：重做 600–1024px 断点与移动端列表/步骤布局。
6. U5–U8：无障碍、文档版本和长表单体验。
7. 之后再做跨边缘 UDP、真实录音/转码、SMTP/SSO 和公网 TLS 压测。
