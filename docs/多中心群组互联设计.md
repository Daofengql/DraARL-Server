# 多中心群组互联设计

## 1. 设计目标

当前系统曾经按照“一个中心、多个边缘”的方向设计。随着多边缘部署被暂时搁置，后续互联模型调整为“中心到中心”：

- A 主站和 B 主站各自拥有独立的用户、设备、群组、权限和数据库。
- A、B 之间只在明确配置的群组之间转发通信流。
- 两个主站不共享用户，不同步设备，不合并权限，也不互相查询用户密码。
- 远端音频进入本地群组时，以一个系统虚拟设备的身份出现，例如 `Server-A`。
- 互联连接保留明确的发起方和接收方，但发起方不因此获得接收方的管理权限。

典型场景如下：

```text
A 主站的 group-12
        │
        │ 互联对象 bridge-001
        ▼
B 主站的 group-38
        │
        └── 本地群组看到一个虚拟设备：Server-A
```

这里的 `group-12` 和 `group-38` 是两个主站各自数据库中的本地 ID，不要求相同，也不要求建立全局群组表。

## 2. 与中心—边缘模型的区别

中心—边缘模型中，中心是用户、设备和路由的权威来源，边缘主要负责本地接入、fan-out 和缓存中心下发的路由投影。

多中心模型中，A 和 B 都是独立的业务主站：

| 项目 | 中心—边缘 | 中心—中心 |
|---|---|---|
| 用户系统 | 中心统一管理 | 每个主站独立 |
| 设备归属 | 中心统一管理 | 每个主站独立 |
| 群组权限 | 中心权威下发 | 每个主站本地判断 |
| 连接角色 | 中心和边缘 | 发起中心和接收中心 |
| 路由同步 | 中心向边缘投影完整路由 | 只同步互联对象允许的群组映射 |
| 远端来源 | 边缘设备或边缘会话 | 系统虚拟服务器设备 |
| 凭据 | 边缘节点凭据 | 中心间互联凭据 |

因此，现有 Type 0 协议可以继续作为安全控制面和数据面基础，但业务语义应逐步从“中心下发完整路由”收敛为“中心之间传递经过授权的群组桥接流”。

## 3. 连接方向与角色

两台主站不需要被设计成完全对称的连接管理方式。每条互联连接明确记录：

- `initiator_center`：主动建立 TCP/TLS 控制连接的一方。
- `acceptor_center`：监听并接受控制连接的一方。
- `link_id`：双方共同识别的互联对象 ID。
- `credential_epoch`：凭据轮换代数。
- `direction`：允许 A 到 B、B 到 A，或双向。

发起方负责：

- 建立连接。
- 断线重连。
- 发送握手和互联对象声明。
- 发送本地群组产生的桥接流。

接收方负责：

- 验证中心身份和凭据。
- 检查本地是否配置了对应互联对象。
- 检查来源中心、目标群组和方向是否匹配。
- 接收数据并注入本地虚拟设备。

发起方和接收方只是连接生命周期角色。它们不表示谁拥有对方的数据，也不表示谁拥有更高的业务权限。接收方必须显式批准每条入站互联，不能因为握手成功就自动开放所有群组。

如果 B 需要向 A 发起连接，可以建立另一条方向相反的连接，也可以在同一条双向连接上启用反向转发，具体取决于部署网络和防火墙条件。业务方向必须由互联对象配置决定，不能由 TCP 连接方向自动推断。

## 4. 互联对象

建议把跨中心关系抽象为 `InterCenterLink`，而不是把远端群组伪装成本地群组。

建议字段如下：

```text
id
link_id
local_center_id
remote_center_id
local_group_id
remote_group_id
initiator_center_id
direction                 # one_way_forward / one_way_reverse / bidirectional
enabled
accepted
forward_audio
forward_text
forward_broadcast
virtual_device_name
credential_epoch
last_connected_at
last_error
```

如果一个主站希望把多个本地群组连接到同一个远端群组，应创建多个明确的互联映射，避免用隐式规则扩大转发范围。

双方最好都保存本地配置：

- 发起方保存出站目标、远端地址和本地转发规则。
- 接收方保存入站批准、来源中心、目标群组和允许的媒体类型。

这样即使一方配置泄漏，另一方没有批准记录时也不会接收业务流量。

## 5. 音频转发流程

以 A 的 `group-12` 转发到 B 的 `group-38` 为例：

1. A 的本地设备或客户端先按 A 的本地权限发送音频。
2. A 根据本地互联映射判断 `group-12` 是否允许转发到 B。
3. A 不把用户密码、JWT、数据库用户 ID 或设备认证信息发送给 B。
4. A 将音频封装成中心间互联帧，包含来源中心、互联对象、媒体类型、序列号和时间信息。
5. B 验证 TLS 会话、互联凭据、`link_id`、方向、目标群组和消息新鲜度。
6. B 将音频注入 `group-38`，来源设备固定为虚拟设备 `Server-A`。
7. B 按本地群组的普通 fan-out 逻辑发送给本地用户和设备。

远端音频不需要解析呼号，也不需要还原远端用户身份。协议层只需要识别媒体类型和负载；展示层使用配置好的虚拟设备名称。

双向互联时，B 到 A 的流量使用另一个方向的映射，在 A 中显示为 `Server-B`。两边的虚拟设备身份互不共享，也不应复用普通用户设备的 SSID、设备密码或用户 ID。

## 6. 虚拟服务器设备

远端来源在本地主站应被视为一种特殊的系统设备：

- `source_type = intercenter`
- `virtual_device = true`
- `center_id = 远端中心 ID`
- `link_id = 互联对象 ID`
- `device_name = Server-A` 或管理员配置的名称
- `owner_id = null` 或系统保留 owner
- 不绑定本地用户
- 不参与普通设备注册和设备密码认证

虚拟设备可以拥有在线、离线和错误状态，但它的在线状态表示互联连接和映射可用，不表示某个用户在线。

建议为每条方向映射生成稳定的内部虚拟设备标识，例如：

```text
intercenter:{remote_center_id}:{link_id}:{direction}
```

这样可以避免连接重连后产生重复设备，也能让通信记录按同一个远端来源持续归档。

## 7. 通信记录与统计

互联音频进入本地群组后可以正常参与本地转发和统计，但来源语义必须保持为系统互联源：

```text
source_type       = intercenter
source_center_id  = center-a
link_id           = bridge-001
virtual_device    = Server-A
local_group_id    = 38
remote_group_id   = 12
user_id           = null
device_id         = null 或虚拟设备 ID
```

建议同时记录：

- 接收包数、转发包数、字节数
- 丢包、过期包、重放包和校验失败数
- 首包时间、末包时间和会话持续时间
- 互联连接状态和最后错误
- 远端中心和互联对象

不要把远端音频错误归因到本地用户，也不要伪造呼号或用户 ID。后台可以显示“Server-A → 本地群组”，而不是显示一个无法在本地查询的远端用户。

## 8. 安全边界

中心间互联必须先通过传输层认证，再进行业务映射校验。至少需要检查：

- TLS 证书或长期互联凭据
- 中心 ID 与凭据绑定关系
- 凭据代数和吊销状态
- `link_id` 是否存在且启用
- 来源中心是否与互联对象一致
- 转发方向是否允许
- 目标群组是否仍存在且启用
- 帧序列号、时间戳和重放窗口
- 单连接包速率、字节速率和队列长度

互联消息不能携带可直接用于本地登录的用户凭据，也不能让远端中心直接调用本地用户、设备或管理员 API。

需要防止以下问题：

- A→B→A 的循环转发
- 同一帧通过多条桥重复注入
- 连接重连后的旧帧继续生效
- 远端伪造本地用户身份
- 远端配置扩大到未批准群组
- 互联断开后队列无限积压

建议每个互联帧携带：

```text
origin_center_id
origin_link_id
message_id
sequence
hop_count
created_at
media_type
payload
```

本地主站收到自己曾经产生的 `origin_center_id` 和 `message_id` 时应直接丢弃。一般情况下 `hop_count` 应限制为 1，除非未来明确支持多级中心桥接。

## 9. Type 0 的调整方向

当前 Type 0 已经具备 TLS 控制面、UDP 数据面、认证、心跳、数据转发和设备配置下发等基础能力。未来可以保留协议框架，但把角色名称和业务语义调整为中心间互联：

- `CenterRuntime` 保留为互联服务端运行时。
- 原来的边缘连接端能力迁移到中心间发起端连接器。
- 节点会话改名或兼容为 peer link session。
- 设备级完整路由投影改为互联对象级群组映射。
- 设备配置下发和边缘设备会话逻辑不再作为多中心桥接的必需路径。
- 设备下行数据仍可保留为底层能力，未来用于指定中心之间的定向传输。

连接协议可以继续复用现有的控制帧、心跳、凭据轮换和 UDP 信封，但入站数据的最终处理点应改为“本地虚拟服务器设备注入器”，而不是本地普通设备认证器。

## 10. 与接入点发现的关系

`GET /api/access-points` 是设备选择接入主站的发现接口，不负责建立中心间互联。

当前阶段：

- 每个主站只返回自己的主接入点。
- 返回公网 UDP 地址和端口。
- 不返回远端中心的用户、群组或互联凭据。
- 多收发器和多个主站入口暂不加入返回列表。

未来增加多个收发器时，可以扩展同一个列表接口；这和中心间群组桥接是两个独立问题，不应把接入点发现和互联授权混在一起。

## 11. 分支和代码迁移思路

当前本地分支安排：

- `dev`：主中心版本。保留中心互联基础设施、群组互联、Type 0 控制能力和主中心接入点发现；不提供独立 edge 启动入口。
- `edge`：保留原有无数据库边缘运行时，作为以后需要边缘接入时的兼容分支。

后续把中心—边缘语义调整为中心—中心时，建议按以下顺序处理：

1. 先抽象 `CenterPeerLink` 或 `InterCenterLink`，不要直接复用 `EdgeNode` 作为最终业务名称。
2. 保留现有 TLS、凭据轮换、心跳、重连和 UDP 信封机制。
3. 将群组映射和转发方向放到独立的互联对象中。
4. 在本地增加虚拟服务器设备适配层。
5. 先实现单向音频 A→B。
6. 验证本地群组权限、通信记录、断线重连、重复包和循环转发。
7. 再增加 B→A 和双向映射。
8. 最后再考虑文本、广播、动态端口和多个主站之间的复杂拓扑。

不建议一开始同步用户、设备或完整群组路由。只做明确群组之间的媒体桥接，能够保持两个主站的业务边界，也更容易控制安全和故障范围。

## 12. 暂不实现的内容

本设计当前只作为后续实现依据，本轮不增加以下功能：

- 多收发器接入点列表
- 多主站自动发现
- 用户或设备跨中心同步
- 全局统一登录
- 多级中心转发
- 自动选择最优中心
- 跨中心远程管理
- 自动端口轮换

当前重点是保留互联基础设施，并把未来目标明确为“独立主站之间的群组媒体桥接”。
