# UDP 单机转发压力测试

本文记录 DraARL 单机 UDP 服务在大量在线设备下的本地 fan-out 压力测试。测试日期为 2026-07-19，基线代码为 `dev` 分支提交 `2a78514`。

这是一组本地容量实验，不是生产 SLA。结果适合识别代码瓶颈和确定后续优化方向，不能替代目标 Linux 服务器、真实网卡和真实网络环境下的复测。

## 结论

- `5 个独立群组 × 每组 1000 台设备 × 5 人同时发言`，普通语音和录音开启时零丢包。
- 单个超大群组比相同总设备数的多个小群组更容易丢包，主要限制是单帧 fan-out 批次，而不只是平均包速。
- 单组 120ms 合包间隔下，5000 个接收端零丢包；5500 开始进入灰区，6000 丢包约 5.7%。
- 单组 60ms 间隔下，3000 个接收端零丢包；3100 开始进入灰区，3200 丢包约 5.9%。
- 实际下行平台约为 5 万次 UDP 写出/秒、165 Mbps DraARLv1 应用层流量，但 8000 至 9000 人的超大单帧批次会更早触发队列丢弃。
- 过载时服务端仍只使用约 1.3 至 1.4 个逻辑核，当前首先撞到的是发送队列、单 socket 写出和突发批次，而不是整机 CPU。
- 仅考虑业余无线电的常规容量，目前没有必须立即实现集群的证据。集群仍可用于异地接入、高可用和拆分超大群组。

## 测试环境

| 项目 | 配置 |
|------|------|
| 操作系统 | Windows，本机 UDP 回环 |
| CPU | AMD Ryzen 9 7940HX，16 核 32 线程 |
| 内存 | 64 GB |
| UDP 服务 | 当前 DraARL 单机进程，端口 `60050` |
| MySQL | 本机 MySQL 8.0.12 |
| 完整报文 | 410 字节：90 字节 DraARLv1 头部 + 320 字节 DATA |
| 心跳 | 每台模拟设备约 2 秒一次 |
| 最大规模 | 37 个测试用户、9000 台测试设备 |

## 测试方法

压测工具位于 `test/bench/udp_fanout`。每台模拟设备都执行以下流程：

1. 在 MySQL 中建立带固定测试前缀的用户、设备和群组。
2. 创建独立 UDP socket，通过真实 DraARLv1 心跳完成设备认证和上线。
3. 按群组安排一个发言设备，使用真实语音路由路径发送带测试编号和时间戳的数据包。
4. 接收端统计与理论 fan-out 数量，计算丢包率和本地处理延迟。
5. 采集 DraARL 服务进程和压测进程的 CPU、RSS。
6. 结束后删除测试用户、设备、群组、通信记录和本地录音文件。

每个客户端绑定不同的 `127.x.x.x` 地址。这样仍保留每地址 150 pps 和每 IP 600 pps 的限速代码，但不会让同一个回环 IP 的粗限速成为测试上限。

`Type=6` 用于隔离纯 UDP 路由与 fan-out；`Type=5` 用于验证普通设备语音、录音队列、录音上传和通信记录开启后的完整路径。

## 多个独立群组

以下场景都使用普通 `Type=5` 语音、120ms 间隔并保持录音开启，总设备数固定为 5000。

| 群组布局 | 同时发言 | 实际下行 | 应用层带宽 | 丢包率 | 平均延迟 | 服务端 CPU |
|----------|---------:|---------:|-----------:|-------:|---------:|-----------:|
| 1 × 5000 | 1 | 41,897 pps | 137.42 Mbps | 0.225% | 54.4ms | 1.19 核 |
| 2 × 2500 | 2 | 41,639 pps | 136.57 Mbps | 0.028% | 52.2ms | 1.20 核 |
| 5 × 1000 | 5 | 41,625 pps | 136.53 Mbps | 0% | 48.3ms | 1.18 核 |

单组 5000 的一次普通语音测试出现了轻微瞬时抖动；同规模纯转发重复测试为零丢包，普通语音 5500 人测试也曾出现零丢包。因此百分之零点几的单次差异不应被当作固定边界。

多个独立群组没有表现出额外的全局锁瓶颈。相同总下行量下，小批次、多群组比单个超大 fan-out 更稳定。

## 瓶颈分析

### 发送队列和批次大小

`internal/udphub/fanout_sender.go` 中的全局发送队列容量为 8192，并分给最多 8 个 worker，每个分片约 1024 个槽位。每个目标地址对应一个 `fanoutJob`，分片队列满时会直接增加 `drops` 并丢弃任务。

8000 至 9000 个接收端意味着一次语音帧需要突发提交接近或超过整个队列容量，与该档位的明显丢包一致。增大队列只能用延迟换丢包，过期语音排队太久同样没有价值。

### 全局提交锁

所有 fan-out 批次通过同一个 `submitMu` 提交。它保证同一批次不会与另一批次交错，但也让不同群组的入队阶段串行化。当前 `5 × 1000` 没有触顶；更多高负载群组仍可能在这里排队。

### 大切片分配

`internal/udphub/domain_receiver_cache.go` 只回收容量不超过 4096 的地址切片。超大群组会在每一帧创建新的大切片，增加内存分配和 GC 压力。测试期间服务端 RSS 从约 80 MB 上升到最高约 163 MB，测试结束后 Go 堆保留了部分已申请内存；该现象不足以单独判定为泄漏。

### 单 socket 写出

8 个发送 worker 最终都对同一个 UDP socket 逐地址调用 `WriteToUDP`。过载时 CPU 使用率仍然较低，符合系统调用、队列突发或本机 UDP 栈先成为限制的表现。Linux 上使用批量发送能力后可能得到不同结果。

### 设备缓存上限

`internal/udphub/device.go` 和 `internal/udphub/server.go` 使用 `ListDevices(10000, 1)` 加载设备。超过一万台持久化设备后可能出现缓存不完整，这不是压测推测，而是当前代码中的明确上限，应在扩容或集群之前修正。

### 限速器

当前限速为每 `IP:端口` 150 pps、每 IP 600 pps。它没有成为本次测试瓶颈，但大量设备共用同一 NAT 或代理出口时，聚合心跳也可能触发每 IP 上限。该问题与 fan-out 容量独立，集群不会自动解决。

## 容量建议

本机测试的保守零丢包区间如下：

| 语音包间隔 | 单群组建议上限 |
|------------|---------------:|
| 60ms | 2500 台接收设备 |
| 120ms | 4000 台接收设备 |
| 180ms | 5000 台接收设备 |

整机持续下行建议先控制在 35,000 至 40,000 pps，为系统抖动、WebSocket、数据库同步、录音上传和真实网络保留余量。

对于业余无线电业务，单群组持续在线数千台设备已经属于很大的规模。建议先完成以下工作，再以性能为理由实施集群：

1. 暴露 fan-out、UDP 收包流水线和录音队列的 `queued/sent/drops` 指标。
2. 修正设备缓存 10000 条硬上限。
3. 复用超过 4096 个地址的切片或采用分块快照。
4. 在目标 Linux 服务器和真实网卡上重复本工具的基准矩阵。
5. 评估 Linux 批量 UDP 发送，减少逐地址系统调用。

如果出于异地接入、高可用或超大群组需要集群，中心节点应只向每个目标 UDP 子节点发送一份语音，由子节点完成本地 fan-out。这样集群才能真正把一个大接收表拆成多个小批次。

## 复现

单组分档测试：

```bash
go run ./test/bench/udp_fanout -confirm-test-data -server-pid 11396 -levels 1000,2000,4000,5000 -duration 10s -interval 120ms
```

5 个群组、每组 1000 台设备：

```bash
go run ./test/bench/udp_fanout -confirm-test-data -server-pid 11396 -groups 5 -levels 5000 -duration 15s -interval 120ms -packet-type 5
```

具体参数、安全说明和异常中断后的清理方式见 `test/bench/udp_fanout/README.md`。
