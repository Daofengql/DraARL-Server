# 数据库迁移与回退

使用既有 GORM AutoMigrate 和 schema_migrations 版本记录，不再增加迁移引擎。启动通过 MySQL advisory lock 串行迁移，状态区分 running/completed，仅已完成版本可以跳过。当前显式迁移到版本 5，代码实现为准。

## 变更规则

先加可空字段/新表，再回填和加约束；回填可重试、有边界，并添加真实 MySQL 的失败恢复/二次启动测试。不要关闭外键校验掩盖错误。设备未分组用 NULL，保留群组删除 ON DELETE SET NULL。MySQL DDL 可能隐式提交，不能认为 GORM 迁移可整体事务回滚。旧 wall-clock DATETIME 不应在不知道原时区时整体平移。

## 升级流程

从 `v2.0.1-alpha13` 起，可用新版本程序单独执行迁移；读取原配置，完成数据库迁移后退出，不启动 HTTP/UDP、Redis 认证或后台任务：

```bash
./DraARL-linux-amd64 -c /path/to/config.yaml -migrate-only
```

该命令同时执行版本化迁移和幂等 schema 同步，失败返回非零状态。普通启动不会自动迁移已有数据库。Release 的 Supervisor 自动部署会在停服后调用该命令，迁移成功才替换程序并恢复服务。数据库备份由宝塔定时任务负责，部署期间不额外导出 SQL；迁移开始后的失败保留旧程序和日志、保持停服，等待核对数据库状态。

1. 停止入口写入、后台播报和中心，记录旧版本、镜像摘要、配置、密钥及迁移版本。
2. 数据库备份由宝塔定时任务负责，部署不重复导出 SQL；对象/本地存储、配置和密钥按现有备份策略管理。
3. 数据库副本先运行新版本，确认迁移、空群组设备、登录/撤销、UDP/WS、音频和文件访问。
4. 单个中心执行生产迁移，确认没有 running 遗留，再恢复流量。不要让多个不同版本同时改库。

## 回退

仅新增且已验证旧程序兼容的变更，可停新程序、切换旧二进制并保留数据库。清洗/删除/约束或语义变化需要停写，将升级前备份恢复到新库，用配套旧配置、密钥和对象快照验证后再切入口。升级后新写入不会自动并回旧快照，恢复前决定需要保留的数据。

不要手动把失败迁移改为 completed。检查部分落地 DDL、保留备份和日志，修复原因后重试幂等迁移。`go run ./tools/integration -only migration-recovery,authentication` 验证迁移恢复及重复启动，不能代替生产数据副本演练。

## 版本 5：单节点设备接入

迁移保留现有入口 ID、地址和端口，忽略旧发布状态，移除旧发现选项、边缘设备归属、群组主从服务器字段及边缘凭据／投影字段。旧服务器基础目录行作为历史数据保留，应用不再访问。用户、空群组设备、群组、站间互联会话保持完整。旧边缘配置被忽略。迁移可重复运行，但回退到依赖旧字段的版本需要恢复配套数据库备份。
